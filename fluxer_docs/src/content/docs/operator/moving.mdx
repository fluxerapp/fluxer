Until late 2026, Fluxer ran each of its parts in its own container with Docker Compose, installed by rexctl or by hand. New releases run as one container or one systemd service, and you can move an older instance to either.

rexctl is optional. The `compose.yaml` and `fluxer.env` that each release publishes are a supported way to run Fluxer without it, as in the [Docker guide](/operator/docker/). From the older layout you get there once with `rexctl migrate --to compose`, or with `rexctl detach` after a move to one container. rexctl then leaves Fluxer alone.

| You have | You want | Command |
| --- | --- | --- |
| The older layout, from rexctl or set up by hand | rexctl runs Fluxer in one container | `rexctl migrate --to docker` or `--to podman` |
| The older layout | rexctl runs Fluxer as a systemd service | `rexctl migrate --to systemd` |
| The older layout | `compose.yaml` and `fluxer.env` that you run yourself | `rexctl migrate --to compose` |
| One container that rexctl runs | `compose.yaml` and `fluxer.env` that you run yourself | `rexctl detach` |
| `compose.yaml` and `fluxer.env` that you run yourself | rexctl runs Fluxer | `rexctl adopt` |

## What happens to older installs

They keep running on the release they have.

`rexctl status` shows that this instance uses the older layout and won't get new releases, and the command still exits with code 0.

`rexctl upgrade --yes` and nightly upgrades never move an instance on their own. In a terminal, `rexctl upgrade` offers the move. It changes nothing unless you say yes.

The older layout gets no more releases, and that includes security fixes.

## One container or systemd?

Both run the same Fluxer with the same settings, and rexctl manages either.

- One container works on any Linux machine with Docker or Podman. It keeps everything in one container with its own PostgreSQL 17, and it is the closest to the old layout. It is also the one you can run yourself from `compose.yaml`.
- systemd runs Fluxer as one service on the machine, on Debian 12 or later or Ubuntu 22.04 or later. It needs root and a folder that only root can change, such as `/opt/fluxer`, and it uses the machine's PostgreSQL 16 or newer.

### On NixOS

On NixOS, `/etc/systemd/system` comes from your configuration and rexctl can't write to it. Move to one container with `sudo rexctl migrate --to docker`, or `--to podman`. Docker starts the container again after the machine restarts. Podman does that when `podman-restart.service` is on, which you turn on with `systemd.services.podman-restart.wantedBy = [ "multi-user.target" ];` in `configuration.nix`. `--to systemd` stops before it changes anything.

rexctl can't add the timers for [automatic upgrades](/operator/upgrades/) and [scheduled backups](/operator/backups/) either. When you turn one on, or when the old instance had one, rexctl prints the `systemd.services` and `systemd.timers` lines for `configuration.nix` that run the same rexctl commands. Add them and run `sudo nixos-rebuild switch`. Until you do, `rexctl status` shows a "Timers" row, and `rexctl doctor --verbose` shows the lines again.

## What the move does

`rexctl migrate` moves an instance in one go and checks that it works.

1. Backs up your instance.
2. Stops Fluxer's containers and leaves them in place with their volumes.
3. Downloads the newest Fluxer.
4. Creates the new Fluxer, in one container or as the systemd service.
5. Restores the backup and starts Fluxer.
6. Checks that it works. If not, removes the new one and starts the old containers again.

With `--to compose`, rexctl then writes `compose.yaml` and `fluxer.env` into the new folder, starts Fluxer from them with docker compose and checks it again.

An install on a release before 2026.1111.22825 can't move off Valkey and SeaweedFS while it runs. The move then copies that data while the old containers are stopped, and the old containers keep their own copy.

Your address, ports, settings, admins, users, messages and uploads stay the same. Fluxer gets new certificates. In one container, its own PostgreSQL moves from version 16 to 17 by a dump and restore. Under systemd, it moves to the newest PostgreSQL on the machine, which must be 16 or later. Your own PostgreSQL stays as it is. The move needs free disk for a second copy of your uploads, and the instance is offline for a few minutes while it runs.

## Move and keep using rexctl

<Steps>

1. Update rexctl to the newest release.

   ```sh
   curl -fsSL https://fluxer.dev/install.sh | sudo sh
   ```

   It prints `Installed rexctl` followed by the new version number.

2. See what the move would do, without changing anything.

   ```sh
   sudo rexctl migrate --to docker --dry-run
   ```

   It lists the steps above with your domain and the disk space the move needs.

   Use `--to podman` for Podman, or `--to systemd` to run Fluxer without containers on Debian or Ubuntu. Older installs run PostgreSQL 16, which is newer than what Debian 12 and Ubuntu 22.04 ship. On those two, install `postgresql-16` or newer from [apt.postgresql.org](https://wiki.postgresql.org/wiki/Apt) before you start the real move.

3. Move.

   ```sh
   sudo rexctl migrate --to docker
   ```

   Each step prints as it finishes, then the address where Fluxer runs.

   The old containers stay stopped.

4. Sign in to your instance in the browser. When your messages and uploads are there, remove the old containers and volumes.

   ```sh
   sudo rexctl migrate --clean-up
   ```

   It lists what it removed. If you skip this step, `rexctl status` reminds you about the old containers from 14 days after the move.

</Steps>

## Move and run it yourself with docker compose

<Steps>

1. Update rexctl to the newest release, as above.

   ```sh
   curl -fsSL https://fluxer.dev/install.sh | sudo sh
   ```

2. See what the move would do, without changing anything.

   ```sh
   sudo rexctl migrate --to compose --dry-run
   ```

   It lists the steps with the new folder, such as `/opt/fluxer-container` for `/opt/fluxer`. `--new-dir` picks another one.

3. Move.

   ```sh
   sudo rexctl migrate --to compose
   ```

   rexctl moves Fluxer into one container in the new folder and checks it, then writes `compose.yaml` and `fluxer.env` there and starts Fluxer from them with docker compose. On Podman it uses `podman compose`. The card at the end shows the commands for the new folder.

4. Sign in to your instance in the browser. When your messages and uploads are there, remove the old containers and volumes.

   ```sh
   sudo rexctl migrate --clean-up
   ```

   It also removes rexctl's own files from the new folder. From then on, rexctl manages nothing there, and you [run Fluxer like any Docker install](/operator/docker/#moved-here-with-rexctl). If nothing else on the machine uses rexctl, the last line shows which file to delete to remove rexctl itself.

</Steps>

If you moved to one container with `--to docker` earlier, `rexctl detach` in the new folder gives you the same two files.

After the move, `custom.compose.yml` no longer applies. Network changes it made, such as other ports, become rexctl settings, or with plain compose, edits in `compose.yaml`.

## Going back

To go back before you clean up, run `sudo rexctl migrate --undo`. It backs up the new instance, removes it and starts the old containers with their data. Anything posted after the move is lost, and changes to Valkey or SeaweedFS stay. With your own PostgreSQL, rexctl can't go back, because the newer release has already updated the database.

After `--to compose`, `--undo` stops Fluxer in the new folder and backs up its volume into the `backups` folder there. It renames `compose.yaml` and `fluxer.env` to `compose.yaml.undone` and `fluxer.env.undone`, starts the old containers and keeps the new volume. It prints the command that removes that volume once you're sure you don't need it.

## Clean up

Remove the old containers and volumes with `rexctl migrate --clean-up`, never with `docker compose down -v`. rexctl removes only the old containers of this instance and their volumes, and leaves alone any container that runs from another folder, such as the one `--to compose` started.

## What stops a move

- For a `custom.compose.yml` with changes the new layout can't take over, rexctl lists each line and what it needs. Most of them move into settings with `rexctl config set`.
- For voice servers in Docker on the same machine, remove them with `rexctl voice remove` first, and add them again after the move. Voice servers on other machines keep running and need nothing.
- For a setting the new layout doesn't use, rexctl says which one it is. Remove that setting first with `rexctl config unset`.

An external PostgreSQL or S3 store moves along as settings, as does automatic upgrading.

## Data in folders and custom.compose.yml

rexctl takes over these parts of `custom.compose.yml` as they are, so you don't need to empty it:

- Folders on the machine that hold the data of PostgreSQL, Valkey, NATS, Meilisearch, SeaweedFS or the edge, in place of their volumes. The backup and the move read the data from those folders.
- Volumes that only set `external: true` and their usual name, such as `fluxer_seaweedfs-data`.
- A folder for the temporary files of the media proxy. The new layout has its own, so the move leaves this one out.
- A Caddyfile for the edge that is the same as the one rexctl writes, such as a copy of it in the instance folder. If you changed it, put your directives in a `.caddy` file in `caddy.d` first.
- Edge ports that a setting can give too. rexctl says which command to run first, such as `rexctl config set edge.bind=127.0.0.1:5580`.
- A read-only folder with the GeoIP database for the api and worker. rexctl copies the file that `FLUXER_GEOIP_DB_PATH` points at into the `geoip` folder of the new instance and sets [`geoip.database`](/operator/configuration/#geoip-database).

If the file replaces the volumes of the api, the worker or the media proxy with `!override`, remove `!override` from that line first. The move off SeaweedFS adds a volume for the uploaded files to them, and `!override` would drop it.

Before it changes anything, rexctl checks that the containers ran on the folders and volumes listed in the file. Don't empty the file or remove a folder line to get past a refusal. The backup would then hold none of the data in those folders, and the old containers would start on new empty volumes.

If the move goes back, the old containers start with the same file and the same folders. rexctl refuses to start them when the file would give a service another volume or folder than the one that holds its data. rexctl records those folders and volumes when the move starts, so the check works even when the old containers are gone.

When the old containers kept data in folders, the move to one container or to compose puts all of Fluxer's data in a new folder next to them, called `fluxer-data`. That keeps the data on the same disk, and the plan shows the folder. Pass `--data-folder` with another empty folder, or `--data-folder=""` for a volume of Docker or Podman. [Keep data on another disk](/operator/configuration/#keep-data-on-another-disk) has more about the folder.

The old folders stay on the machine after the move. `rexctl migrate --clean-up` lists them and never deletes them. Delete them yourself once the new instance has your data.

## Installs you set up by hand

The same commands work in a folder where you set up the older layout yourself from `fluxer-compose-<version>.tar.gz` and started it with `docker compose up -d`. Run them in that folder, or pass `--dir`. rexctl can also run straight from the install script there.

```sh
cd ~/fluxer
curl -fsSL https://fluxer.dev/install.sh | sh -s -- migrate --to compose --dry-run
```

- The compose files must be the ones from the release you run, as they came out of the archive. rexctl downloads that release's archive and compares each file.
- Put your own changes in `custom.compose.yml` and list it in `COMPOSE_FILE` in `.env`. rexctl refuses a second file of changes, an edited release file, and a file that uses `include`, `build`, `env_file` or `extends`.
- rexctl reads the release from `FLUXER_IMAGE_TAG` in `.env`. Without it, rexctl expects 2026.1124.80040, the last release with these files. For an older release, set `FLUXER_IMAGE_TAG` to it first.
- rexctl keeps a record in `.rexctl` in that folder, puts backups in `backups` and leaves your files as they are. When the move changes Valkey or SeaweedFS on the running instance first, rexctl updates `.env` to match and keeps the old one as `.env.before-rexctl`. If `.env` then lists a compose file from the release that the folder doesn't have, rexctl copies that file in from the release. Your own files then still describe what runs.
- Until the move is over, leave the files in that folder as they are. rexctl compares them with its record and refuses to act on the old containers when one changed. A copy of each is in `.rexctl/handrun`. While the record is there, rexctl runs only `rexctl migrate`, `rexctl status` and `rexctl logs` in that folder.
- `rexctl migrate --clean-up` removes the record along with the old containers. To remove the record without a move, or after `--undo`, run `rexctl migrate --forget`. Your compose files, `.env` and backups stay. Once rexctl has updated `.env`, `rexctl migrate --undo kv` and `--undo storage` refuse, because `.env` would no longer match what runs.

A folder that the old `rexctl eject` left works the same way. rexctl keeps the old record in `.rexctl/state.ejected.json`.

## Where is fluxer-compose-\<version>.tar.gz?

Releases up to 2026.1124.80040 shipped `fluxer-compose-<version>.tar.gz` with the older layout. Newer releases ship `compose.yaml` and `fluxer.env` for one container in its place. `rexctl migrate` takes you from the archive to those files, and the [Docker guide](/operator/docker/) covers them from then on.

Older links to `rexctl takeover` now mean `rexctl migrate` for the older layout, or `rexctl adopt` for a Fluxer you run from `compose.yaml`.

## Moving from the 0.x chart

The 0.x chart ran each part of Fluxer as its own workload, with its data in PostgreSQL, NATS, Valkey and SeaweedFS. The new chart refuses to upgrade a release of it, because the upgrade would start an empty instance.

:::caution[Use a new release name]
Argo CD and `helm template` can't run that check. Never point an existing Argo CD application or a [Flux CD](https://fluxcd.io/) HelmRelease at the new chart, because that would remove the old workloads and start an empty instance.
:::

To move, install the new chart under a new release name in the same namespace, and copy the data with `fluxerd import`.

It fetches the 0.x database, Valkey, NATS streams and uploads over the cluster network, keeps the 0.x keys that stored data depends on, and writes one archive for `fluxerd restore`. The 0.x chart gets no new releases, not even security fixes.

The steps use `fluxer` for the 0.x release, `chat` for the new one and the namespace `fluxer`. The new volume needs room for the uploads and the database twice over.

### Values

Write a values file for the new release with the same `domain` as before.

| 0.x value | Goes to |
| --- | --- |
| `env` | `config` |
| `secrets.extra` | A Secret that `existingSecret` points to |
| `secrets.existingSecret` | The import command, in place of `secret/fluxer-env secret/fluxer-unfurl-env` |

Leave `postgres.externalSecret` empty, because `fluxerd restore` loads the import only into the PostgreSQL that runs in the pod.

### Steps

<Steps>

1. Note how many replicas each 0.x Deployment runs, then stop the 0.x parts that write. This also frees the 0.x voice ports, and its databases keep running.

   ```sh
   kubectl -n fluxer get deployment -l app.kubernetes.io/instance=fluxer \
     -o custom-columns=NAME:.metadata.name,REPLICAS:.spec.replicas --no-headers > fluxer-0x-replicas.txt
   kubectl -n fluxer scale deployment -l app.kubernetes.io/instance=fluxer --replicas=0
   ```

2. The 0.x NetworkPolicy lets in only the 0.x pods. Let the new release in as well.

   ```sh
   kubectl -n fluxer apply -f - <<'EOF'
   apiVersion: networking.k8s.io/v1
   kind: NetworkPolicy
   metadata:
     name: fluxer-import
   spec:
     podSelector:
       matchLabels:
         app.kubernetes.io/instance: fluxer
     policyTypes: [Ingress]
     ingress:
       - from:
           - podSelector:
               matchLabels:
                 app.kubernetes.io/instance: chat
   EOF
   ```

3. Install with `maintenance` on, then import and restore. The import prints the path of the archive that `fluxerd restore` loads.

   ```sh
   helm install chat oci://ghcr.io/fluxerapp/charts/fluxer -n fluxer -f values.yaml --set maintenance=true
   kubectl -n fluxer rollout status statefulset/chat-fluxer
   kubectl -n fluxer get secret/fluxer-env secret/fluxer-unfurl-env configmap/fluxer-config -o json \
     | kubectl -n fluxer exec -i chat-fluxer-0 -- fluxerd import -
   kubectl -n fluxer exec chat-fluxer-0 -- fluxerd restore /var/lib/fluxer/backups/<archive>
   ```

4. Once the restore has finished, remove the 0.x release and start Fluxer. Removing the release keeps its volumes and Secrets.

   ```sh
   helm uninstall fluxer -n fluxer
   kubectl -n fluxer delete networkpolicy fluxer-import
   version=$(helm get metadata chat -n fluxer | awk '/^VERSION:/ {print $2}')
   helm upgrade chat oci://ghcr.io/fluxerapp/charts/fluxer -n fluxer --version "$version" -f values.yaml --set maintenance=false
   ```

5. Search starts empty, so open "Search Index" in the admin panel and choose "Reindex everything". People sign in with their passwords as before.

</Steps>

### If the import or restore fails

The 0.x release is still installed.

Start its parts again and remove `chat`.

```sh
while read -r name replicas; do kubectl -n fluxer scale deployment "$name" --replicas="$replicas"; done < fluxer-0x-replicas.txt
helm uninstall chat -n fluxer
kubectl -n fluxer delete networkpolicy fluxer-import
```

### Going back

To go back after step 4, uninstall `chat` and install the 0.x chart again under the name `fluxer` with its old values. It starts on its kept volumes, without newer data. Once the new release has everything, delete the 0.x volumes and Secrets.

```sh
kubectl -n fluxer delete pvc -l app.kubernetes.io/instance=fluxer
kubectl -n fluxer delete secret fluxer-env fluxer-unfurl-env
```
